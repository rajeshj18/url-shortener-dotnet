# ADR-0010: New code for every create; idempotency keys for retries

**Status:** Accepted · **Date:** 2026-10-21 · **Related:** ADR-0002, ADR-0004, ADR-0005, ADR-0009, FR-08, NFR-04, Assumption A-23

## Context
Two questions to settle:
- Should the same long URL submitted twice get the same code?
- How do we stop a client's retries from creating duplicate links?

The main case: a create times out, for example during a database failover. The client can't tell whether
the link was created, so it retries. The synchronous standby (ADR-0002) guarantees that a committed create
survives the failover, so the retry must return that link rather than make a second one.

## Decision
- **Every create returns a new code** (A-23). Separate links keep analytics and expiry separate.
- **Optional `Idempotency-Key` header**, generated by the **client** (a UUID is recommended): one key per user action, reused for every retry of that action.
  - Format: 1–128 printable ASCII characters; otherwise `400`.
  - **Scoped per API key:** the primary key is `(owner_id, idem_key)`, so different clients can never collide.
- **Request hash:** SHA-256 of the **normalized** request: `longUrl` exactly as sent, `customAlias` or empty, `expiresAt` in UTC to the second or empty, in a fixed order. Whitespace, field order and time-zone notation don't change it.
- **In one transaction on the primary:**
  1. `INSERT INTO idempotency_keys … ON CONFLICT DO NOTHING`
  2. insert the link
  3. store the `201` response body
  4. commit
- **If the key already exists:**
  - older than 24 h (by `created_at`) → treated as absent, and the request proceeds as new;
  - same hash → return the stored `201` body with the header `Idempotent-Replayed: true`;
  - different hash → `422`.
- **Only successful creates are stored.** A `409` or `503` rolls back, so a retry runs again from the start.
- A concurrent duplicate request waits on the primary key until the first transaction finishes, then follows the rules above.
- **Retention is 24 h.** After that, the same request creates a new link. This is documented for clients.
- The full end-to-end flow, with every branch and scenario, is in **LLD §6.1, "Idempotency flow"**.

## Alternatives considered
| Option | Why not chosen |
|---|---|
| Deduplicate by long URL | Mixes analytics; ignores differences in requested options; reveals what others have shortened. The engineer chose to keep A-23. |
| No idempotency | Retries after a timeout create duplicate links |
| Hash the raw request body | Whitespace or field-order differences would cause false `422`s |
| Daily partitions, dropped after a day, instead of deletes | Uniqueness would only be enforced within each partition, so a retry across midnight could create a duplicate |
| A separate cleanup service, or `pg_cron` | Another artifact to deploy, or logic hidden in the database. The schema owner (Api) runs the cleanup itself. |

## Consequences
- **Storage on the `links` primary:** worst case ~100M keys/day (≈ 50 GB kept for the 24 h window).
- **Cleanup:** a background task in the Api service, run by one instance at a time under an advisory lock. It deletes expired keys every 5 minutes in batches (index on `created_at`), with autovacuum tuned for the table (LLD §6.6).
