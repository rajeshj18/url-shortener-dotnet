# TSK-15: Bug fix in the merged code (brownfield)

| Field | Value |
|---|---|
| **Stage / phase** | Stage 1 (core) · Scenario 2, brownfield |
| **Risk class** | **High** (authentication responses; error contract) |
| **Depends on** | TSK-13 |
| **Estimate** | 1.5 h |
| **Branch** | `task/TSK-15-bug-fix` |
| **Status** | Draft spec, awaiting engineer approval (batch review TSK-14 to TSK-18) |

## 1. Intent
Fix a **real** defect found in the merged scenario-1 code, the way a brownfield bug fix should go: reproduce it
with a failing test, commit that test first so the failure is visible in the PR, then fix it. No bug is planted
(TSK-08 D2).

## 2. The candidates (found while drafting this spec, on the running stack)
| # | Defect | Evidence | Impact |
|---|---|---|---|
| 1 | **`401` without `WWW-Authenticate`.** RFC 9110 §15.5.2: a server generating `401` **MUST** send a `WWW-Authenticate` header. Ours sends only the problem body. | `curl -i -X POST /api/v1/urls` without a key → `401`, no `WWW-Authenticate` | Standards-compliant clients and API gateways can't tell which scheme to use; some HTTP libraries treat it as malformed |
| 2 | **Two `traceId` formats.** Our exception handlers return the 32-hex trace ID; responses generated by the framework (status-code pages: `401`, unknown-code `404`) return the full W3C `traceparent` (`00-<trace>-<span>-01`). | `GET` an unknown code on Redirect → `"traceId":"00-3631…-70ee…-01"`; a validation `400` → 32 hex | Support searches logs and traces by `traceId`; with two formats, half the copy-pasted IDs don't match the logged `trace_id` |

**Impacted code:** #1 `ApiKeyAuthenticationHandler` (challenge); #2 `ProblemResponses`, the problem-details
customization in `WebPipelineExtensions`. Neither touches the domain, the database or the ID path.

## 3. Scope
| # | Step | Purpose |
|---|---|---|
| 1 | Commit 1: failing test(s) | The test asserts the correct behaviour and **fails** on the current code; CI shows it red in the PR |
| 2 | Commit 2: the fix | The test passes; nothing else changes |
| 3 | Root cause | Written in the PR and the log: why the existing tests didn't catch it |
| 4 | Docs | LLD §3 (error responses), CHANGELOG (Fixed), log |

**Out of scope:** the candidate not chosen (it stays recorded here and in the log for later).

## 4. Constraints
- The failing-test commit must be pushed before the fix commit, so CI records a red run.
- The `required checks` will block merging while the test fails; the fix is pushed in the same PR before review.
- No behaviour change beyond the defect.

## 5. Acceptance criteria
| # | Criterion | How it's verified |
|---|---|---|
| AC1 | A test reproducing the defect, committed first, fails in CI | The PR's first CI run (link in the log) |
| AC2 | After the fix, that test and all others pass | CI |
| AC3 | Root cause and "why it wasn't caught" recorded | PR description and log |
| AC4 | Gates green; docs; log and hours | CI and review |

## 6. AI usage plan
AI writes the failing test, the fix and the root-cause note (`debug.md`, `write-tests.md`); the engineer confirms the test really reproduces the defect before the fix lands, and gives hours when opening the PR.

## 7. Risks
| Risk | Mitigation |
|---|---|
| A required check blocks the PR while the test is red | Expected; the fix follows in the same PR |
| The fix changes other responses | Assertions on the existing `401`/`404` tests stay as they are |

## 8. Decisions for the engineer
| # | Question | Options | Recommendation |
|---|---|---|---|
| D1 | Which defect | (a) #1 `WWW-Authenticate`; (b) #2 one `traceId` format; (c) both, as two failing-test/fix pairs in one PR | **(c)**: both are small, real and independent; two red-then-green pairs show the method twice. If the timebox is tight, **(a)** alone (a MUST-level standards defect on the auth path) |
| D2 | `traceId` format if #2 is fixed | (a) the 32-hex trace ID everywhere (what the logs and Tempo use); (b) the full `traceparent` everywhere | **(a)** |
